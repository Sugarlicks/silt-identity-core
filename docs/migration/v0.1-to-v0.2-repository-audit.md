# SILT Core v0.1 → v0.2 Repository Audit and Migration Map

**Status:** Release-working document  
**Branch:** `release/v0.2-fc1`  
**Canonical v0.2 basis:** SILT Core v0.2 Semantic Architecture — Freeze Candidate 1 (derived from RC4.1)  
**Purpose:** Identify repository material that remains valid, requires remapping, should be archived as v0.1, or is missing before the v0.2 release.

This document is a repository reconciliation record. It does not modify SILT Core semantics.

The v0.2 architectural seam is:

> **Source → Standing → Presentation → evaluation at the encounter**

Profile Expression supplies bounded encounter-relevant conditions for evaluation without becoming a second architectural spine. SILT Core v0.2 contains no universal `Status` object and no universal `Capacity` object.

## Classification vocabulary

- **UNCHANGED** — may remain substantially as-is, subject to version/status wording.
- **RENAMED / REMAPPED** — the underlying concern remains but the v0.1 term, object or framing must be mapped into v0.2 semantics.
- **SPLIT** — a v0.1 construct combines matters that v0.2 now separates.
- **NO LONGER CORE** — must not be presented as a v0.2 Core object or universal rule.
- **MISSING** — required release material does not yet exist in the repository.

### Governance/IPR tension to resolve explicitly

Current governance/contribution text says the public repository may expose only part of a wider SILT architecture and that undisclosed internal structures may exist. That posture sits uneasily with the present standards trajectory, where the v0.2 semantic architecture is intended to be a stable public specification while commercial value may sit in implementation, assurance, training, tooling and services. This should be resolved deliberately in the Governance & IPR Charter rather than left as ambiguous standards language.

## 4. AUT CISRC implementation profile

**Overall classification: UNCHANGED AS TRANSITIONAL IMPLEMENTATION, with explicit migration note.**

The AUT work began against v0.1-era assumptions and should not be rewritten retroactively to look like a native v0.2 implementation. Its value is partly historical: it shows what implementation pressure produced before the v0.2 architecture stabilised.

Required treatment:

1. Keep the AUT implementation profile, schemas, examples and validator as non-normative implementation material.
2. Add a v0.1 → v0.2 migration note classifying AUT elements as `UNCHANGED`, `RENAMED/REMAPPED`, `SPLIT`, `NO LONGER CORE`, or `MISSING`.
3. Make clear that `ALLOW` / `DENY` are profile/runtime outcomes, not SILT Core semantic evaluation outcomes.
4. Map universal `capacity` fields to the relevant v0.2 semantics rather than promoting Capacity back into Core.
5. Preserve delegation/revocation implementation logic where useful, but map delegation to Action + derived Authority and distinguish technical/runtime enforcement from semantic evaluation.
6. Do not infer that AUT’s institutional hierarchy is a universal SILT Authority model.

The existing AUT validator and `validation-result.schema.json` may remain operationally binary because FC1 permits downstream systems to map semantic results into execution decisions. That mapping must be labelled, not conflated with Core.

## 8. Terminology migration

| v0.1 repository term/framing | v0.2 treatment |
|---|---|
| `Status` | **NO LONGER CORE.** Do not recreate under another name. |
| `Principal` as foundational subject | `Participant` as deliberately thin encounter referent. |
| `Capacity` as universal Core object | **NO LONGER CORE.** Encounter-specific role, office, representative basis or legal capacity may remain meaningful under Source/Standing/Authority/Profile Expression without a universal Capacity primitive. |
| `Authority Source` | `Source`, which may ground Standing, Authority, Obligation or another semantic relation. |
| `Mandate Scope` as primary Core object | Authority scope/constraints where relevant; mandate may be a Source or domain-specific form. |
| Delegation as primitive/artefact | Action constituting derived Authority where relevant. |
| `Profile` / `Lex` | `Profile Expression`, bounded and non-exhaustive. No `Lex` in Core v0.2. |
| `ALLOW` / `DENY` as validation result | SILT semantic outcomes are `SATISFIED`, `NOT_SATISFIED`, `INDETERMINATE`; downstream adapters may map them operationally. |
| “Is this action legitimately authorised?” as universal Core question | Too narrow. Evaluation asks which expressed semantic conditions are satisfied, under which applicable Profile Expression(s), for this encounter. |
| SILT as “missing authority layer” | Too narrow. SILT is the semantic encounter layer preserving Source-grounded Standing and related legitimacy semantics across plural orders. |
| Binding as Core conclusion | Downstream/Profile-defined effect, not universal Core conclusion. |

## 9. Release-blocking versus post-release work

### Release-blocking

- install FC1 as the canonical semantic reference;
- reconcile README/overview/positioning/governance/roadmap language;
- prevent v0.1 `/spec` and root schemas from masquerading as v0.2 normative material;
- add conformance artefacts and corrected LCP mapping;
- add CHANGELOG and migration documentation;
- make licensing boundaries explicit;
- remove or clearly archive obsolete Status/Capacity/Lex-era active material;
- complete final repository terminology audit.

### Not a reason to reopen Core

- redesigning AUT into a native v0.2 implementation;
- adding production APIs;
- choosing DID/VC, KERI/ACDC, UCAN, zcap, GNAP or another implementation substrate;
- solving trust-registry interoperability universally;
- completing the private-ordering/MLETR companion mapping;
- designing certification/assurance machinery;
- building a production validator.

## 10. Freeze discipline for repository reconciliation

The repository work MUST NOT become a back door for changing the frozen semantic architecture.

If an old repository artefact cannot be mapped cleanly into FC1, the default response is to archive, label, split or retire the artefact. Core should be reopened only if implementation evidence demonstrates a genuine semantic distinction that FC1 cannot express without distortion.
