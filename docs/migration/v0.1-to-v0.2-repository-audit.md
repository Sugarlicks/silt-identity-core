# SILT Core v0.1 → v0.2 Repository Audit and Migration Map

**Status:** FC1 repository reconciliation record; external review complete  
**Branch:** `release/v0.2-fc1`  
**Canonical v0.2 basis:** SILT Core v0.2 Semantic Architecture — Freeze Candidate 1 (derived from RC4.1)  
**Purpose:** Record how v0.1-era repository material has been reconciled against the v0.2 semantic architecture, distinguish completed repository work from outstanding release packaging, and preserve explicit boundaries where older implementation work remains on its original semantic basis.

This document is a repository reconciliation record. It does not modify SILT Core semantics.

The v0.2 architectural seam is:

> **Source → Standing → Presentation → evaluation at the encounter**

Profile Expression supplies bounded encounter-relevant conditions for evaluation without becoming a second architectural spine. SILT Core v0.2 contains no universal `Status` object and no universal `Capacity` object.

## Classification vocabulary

The semantic classifications used in the original audit remain useful:

- **UNCHANGED** — may remain substantially as-is, subject to version/status wording.
- **RENAMED / REMAPPED** — the underlying concern remains but the v0.1 term, object or framing must be mapped into v0.2 semantics.
- **SPLIT** — a v0.1 construct combines matters that v0.2 now separates.
- **NO LONGER CORE** — must not be presented as a v0.2 Core object or universal rule.
- **MISSING** — required material did not exist at the point of the original audit.

This reconciliation record also distinguishes **COMPLETED**, **OUTSTANDING** and **DEFERRED / SEPARATE WORK** repository actions. Those action statuses do not alter the semantic classification of an artefact.

## 8. Terminology and semantic migration

| v0.1 repository term/framing | v0.2 treatment |
|---|---|
| `Status` | **NO LONGER CORE.** Do not recreate under another name. |
| `Principal` as foundational subject | `Participant` as deliberately thin encounter referent. |
| `Capacity` as universal Core object | **NO LONGER CORE.** Encounter-specific role, office, representative basis or legal capacity may remain meaningful under Source/Standing/Authority/Profile Expression without a universal Capacity primitive. |
| Identity/status-centred position as the basis of encounter legitimacy | **REMAPPED.** Standing is Source-grounded and relational; Presentation is the bounded encounter-specific act or envelope through which the relevant projection becomes available for evaluation. Presentation does not create Standing, and encounter evaluation does not universally constitute or extinguish it. |
| `Authority Source` | `Source`, which may ground Standing, Authority, Obligation or another semantic relation. |
| `Mandate Scope` as primary Core object | Authority scope/constraints where relevant; mandate may be a Source or domain-specific form. |
| Delegation as primitive/artefact | Action constituting derived Authority where relevant. |
| `Profile` / `Lex` | `Profile Expression`, bounded and non-exhaustive. No `Lex` in Core v0.2. |
| One applicable profile or silent receiver precedence | **REMAPPED.** Multiple Profile Expressions may coexist and the same Presentation may be evaluated separately under each. SILT supplies no universal precedence, merger or aggregate result absent an expressed composition rule. |
| `ALLOW` / `DENY` as validation result | SILT semantic outcomes are `SATISFIED`, `NOT_SATISFIED`, `INDETERMINATE`; downstream or implementation-specific systems may map them operationally. |
| Absence or non-expression treated as another validation outcome | **REMAPPED.** Deliberate non-expression is not a fourth SILT outcome. Where a condition does not enter SILT evaluation because bounded expression would materially distort it, no evaluation object is created and no universal conclusion about the underlying condition follows. |
| Technical control, key possession, capability or execution ability used as authority proxy | **SPLIT.** Technical Capability is operational and distinct from semantic Authority. Technical artefacts may provide Evidence or carry/enforce Authority where the relevant Source and Profile Expression give them that effect; technical success alone does not establish Authority. |
| Cryptographic continuity treated as continuity of authority or legitimacy | **SPLIT.** Semantic continuity is distinct from cryptographic continuity. Changes in keys, credentials or capability mechanisms do not by themselves constitute or extinguish Standing, Authority, Attribution, Consent, Reliance or Obligation. |
| Terms or momentary validation used as the whole account of continuing duties | **REMAPPED.** Obligation is a first-class persistent relational state, distinct from Authority and from the document or Action that may evidence, constitute, transfer, alter or discharge it. |
| “Is this action legitimately authorised?” as universal Core question | Too narrow. Evaluation asks which expressed semantic conditions are satisfied, under which applicable Profile Expression(s), for this encounter. |
| SILT as “missing authority layer” | Too narrow. SILT is the semantic encounter layer preserving Source-grounded Standing and related legitimacy semantics across plural orders. |
| Binding as Core conclusion | **NO UNIVERSAL CORE BINDING CONCLUSION.** Binding is a downstream, encounter-specific effect rather than a universal Core primitive. |

## 10. Freeze discipline for repository reconciliation

The repository work MUST NOT become a back door for changing the frozen semantic architecture.

The external reviewer gate is now complete and did not identify a semantic defect requiring FC2. The v0.2 architecture should therefore be treated as semantically frozen for release unless final mechanical validation reveals an actual contradiction or implementation-independent semantic defect.

If an old repository artefact cannot be mapped cleanly into FC1, the default response remains to archive, label, split or retire the artefact. Core should be reopened only if implementation evidence demonstrates a genuine semantic distinction that FC1 cannot express without distortion.

Repository reconciliation, release packaging, AUT/Vietsch v0.1 completion and future compatibility research are separate workstreams. None should silently rewrite another.
